# Local release kit

Regulatory information, not legal advice.

This directory builds the **reproducible, source-independent local release kit**
for the two runnable services:

- **`eu-reg-api`** — label checker + browser playground (default port 8000).
- **`scan-to-check`** — barcode -> ingredients -> existing checker + PWA
  (default port 8010).

It is intentionally **local-only**: building/running it does not publish,
host, create accounts, or incur charges. Hosting is a separate, manually
documented decision (see the runbook generated by the build and the notes at
the bottom of this file).

## Build a release kit from a trusted snapshot bundle

```bash
# 1. Export from a populated, verified checkout (not a fresh clone):
python3 data/scripts/snapshot.py export --root . \
  --output /tmp/annex-verified.zip

# 2. Build the source-independent release kit:
python3 deploy/build_deployment.py \
  --snapshot-bundle /tmp/annex-verified.zip \
  --dest /tmp/eu-release-kit
```

The builder verifies the bundle with the full snapshot verifier, **enforces the
release boundary** (no deferred ECHA data may be distributed), builds ordinary
wheels for the four maintained packages, downloads the **exact pinned** runtime
dependency wheels into a retained `wheelhouse/`, creates a fresh virtualenv **at
the kit's final installation location**, and installs non-editably from that
wheelhouse with `--no-index`. It writes launchers, a release manifest, license
notices and a runbook.

`--dest` must be a NEW directory outside the checkout. The kit is
**source-independent**: it runs with the disposable build checkout moved away
and `PYTHONPATH` unset, and re-installs from the retained wheelhouse with no
network dependency re-resolution (see the runbook).

A fresh clone has no full regulatory snapshot. Follow [snapshot setup](../docs/snapshot-setup.md) first, or supply an existing trusted bundle directly to step 2. Building requires Python, pip and network access for build tools and runtime wheels. The resulting kit is specific to its OS, architecture and CPython major/minor.

## Run and validate

```bash
cd /tmp/eu-release-kit
./run-eu-reg-api.sh        # http://127.0.0.1:8000/
# In a separate terminal in the same kit directory:
./run-scan-to-check.sh     # http://127.0.0.1:8010/
# Stop both services with Ctrl-C before reinstalling.
./install.sh               # recreate .venv from the wheelhouse (offline)
```

Both launchers default their ports correctly with the environment variables
unset (`EU_REG_PORT`/`PORT`), and resolve the snapshot relative to the kit's own
install directory — so a kit copied to a new location (with its prebuilt `.venv`
removed) still runs. `install.sh` resolves a supported host CPython (**`PY_BIN`
if set, else `python3` on `PATH`**), validates the kit inputs **before**
replacing the existing `.venv`, and never depends on the build checkout's
interpreter being present. Its preflight checks:

- **Retained wheel hashes** against `release-manifest.json`, and that the
  wheelhouse is a **non-empty, complete** release (a `{}`/truncated manifest is
  rejected, never accepted as a valid install).
- **Snapshot integrity** against the retained `snapshot-manifest.json`
  file-hash contract, so a corrupt/tampered/non-database snapshot is rejected up
  front rather than installed with a success message.
- **Host target** — the resolved interpreter must be the same CPython
  *implementation*, *major.minor*, and *OS/architecture* as the build host that
  produced the retained wheels (not just a version prefix).

If venv creation or the offline dependency install fails after preflight, the
installer **rolls back to the prior `.venv`** rather than leaving a partial
runtime behind. It uses the venv's bundled pip with `--no-index` (no
`pip --upgrade pip`, no package-index access).

Because `data/processed/*.sqlite` is gitignored, the snapshot is delivered via
the verified bundle (see [snapshot setup](../docs/snapshot-setup.md)). This is the reproducible,
offline path — no official fetch at runtime.

## Make targets

`make deploy-build` (default) **exports** a fresh snapshot bundle from the live
checkout's accepted snapshot into `DEPLOY_BUNDLE` (refusing to overwrite an
existing archive) and then builds a new kit into a new `DEPLOY_DEST`. It refuses
a destination inside the checkout.

`make deploy-build-consume-existing` consumes an **already-existing** trusted
bundle without exporting a new one (e.g. a pin-verified bundle). Override
`DEPLOY_BUNDLE`/`DEPLOY_DEST` as needed.

**`DEPLOY_DEST` is required on every invocation — there is no default.** A
destination inside the checkout (including the old `.local-reference/deploy/...`
default) would be rejected by the builder; instead an empty `DEPLOY_DEST` fails
the preflight with a copyable example before anything is exported or built:

```bash
make deploy-build DEPLOY_DEST=/tmp/eu-release-kit
make deploy-build-consume-existing DEPLOY_BUNDLE=/tmp/verified.zip DEPLOY_DEST=/tmp/eu-release-kit
```

## Coverage honesty

Inspect the supplied snapshot for its exact coverage. The current local snapshot
contains **Annex II–VI** (CosIng) and the supported cosmetic branches of **REACH
Annex XVII entry 70**, sourced separately from an EU legal act. **ECHA (SVHC / Annex XIV / Annex
XVII) is deliberately NOT included** in this release (acquisition is disabled /
deferred). Both services report ECHA as `not_included` across every report
surface (JSON/CSV/text/HTML/CLI and both browser apps) — a coverage gap / scope
exclusion, **never** a clean result. A bundle that verifies but carries deferred
data is rejected for release (export and deployment boundaries both enforce
this).

## Hosting decisions (NOT done here)

Public hosting requires decisions the user must make independently of this
package: host provider/region and data-reuse terms (CosIng EU-reuse, ODbL
product data), TLS/reverse proxy, snapshot delivery + refresh cadence, access
control (this build binds to 127.0.0.1 with no auth), and provider accounts/charges. The local wheel-based kit is implemented; it
does not configure those hosting services.
